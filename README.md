# ModularBlazor.Module.Keywords

Keywords: a runtime module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform)
platform, in [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture) layers. It keeps the tenant's
**concepts**: the people, places, organizations and topics content is about, each a schema.org entity with names in
several languages (SKOS-style preferred, alternate and hidden labels) and `sameAs` links (Wikidata, Wikipedia, ...).
Other modules point at concepts by id (with a name snapshot) and choose them with the `pick-concepts` dialog; the
Taxonomies module links its terms to them, the DynamicFields and Contents modules tag content with them.

## Layout

```
src/WebApi.Modules.Keywords.Core/             Core: ConceptAggregate (Concept, labels, schema.org types, rules, JSON-LD, search keys) and specifications
src/WebApi.Modules.Keywords.UseCases/         use cases: Mediator commands and queries over concepts, returning an Ardalis Result
src/WebApi.Modules.Keywords.Infrastructure/   data: KeywordsDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.Keywords.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/openapi/keywords.json                     the module's OpenAPI document, exported from Web (see "Building")
src/WebApi.Modules.Keywords.Client/           typed API client, generated by NSwag from that document: a hidden client module
src/Module.Keywords/                          Blazor client module: the Keywords pages (/keywords) and the pick-concepts dialog
tests/         UnitTests (Core, UseCases; NSubstitute) and IntegrationTests (Infrastructure on SQLite)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md: layers, dependency rules, adding a feature
```

The module's id, route prefix and database schema are `keywords`; its permissions are `keywords.read` and
`keywords.manage`.

## Concepts

A concept has a schema.org **type** (Thing, Person, Organization, Place, Country, City, Event, DefinedTerm, ... 27 in
all, `GET /concepts/types`), a unique **slug** (letters of any script, digits and hyphens; made from the name when not
given, numbered when taken: `cairo`, `cairo-2`), **labels**, an optional description, `sameAs` URLs and related
concepts. Labels are per language: at most one *preferred* label per language (at least one overall), any number of
*alternate* names (shown, and written as `alternateName`) and *hidden* ones (misspellings, old names: found by search,
never shown). Search ignores case, accents, Arabic harakat, tatweel and alef/ya forms, and Arabic-Indic digits, so
`مصر`, `Égypte` and `egypte` find the same concept when those are among its labels. A concept is never deleted, only
**retired**: it stays resolvable for content that points at it but leaves the lists and the picker.

| Method and route (under `/api/keywords`) | Permission | Use case |
| --- | --- | --- |
| `GET /concepts?page=&pageSize=&search=&type=&language=&includeRetired=` | `keywords.read` | One page by name; `type` is an exact schema.org type, `language` picks the names shown |
| `GET /concepts/lookup?ids=1&ids=2&language=` | `keywords.read` | The concepts with these ids, in the order asked (retired too) |
| `GET /concepts/types` | `keywords.read` | The schema.org types, each with its parent |
| `GET /concepts/{id}` | `keywords.read` | The concept with every label |
| `GET /concepts/{id}/jsonld?language=` | `keywords.read` | `{ id, name, jsonLd }`: the concept as schema.org JSON-LD, ready for a page's `about` or `mentions` |
| `POST /concepts` `{ type, labels, slug?, description?, sameAs?, related? }` | `keywords.manage` | 201; a slug given and taken is a 409 |
| `PUT /concepts/{id}` `{ version, values }` | `keywords.manage` | 409 if the concept changed since `version`; no slug keeps the current one |
| `POST /concepts/{id}/retire`, `POST /concepts/{id}/restore` `{ version }` | `keywords.manage` | Retire it, or bring it back |

Every call needs a signed-in caller in a tenant (`X-Tenant` header or the token's tenant). The setting
`Keywords:MaxPageSize` (default 100) caps the page size and the ids per lookup; change it on the Host Modules page.

In the Blazor client, the **Keywords** menu entry opens the concept list (`/keywords`: search, type filter, retired
too) and the editor (`/keywords/concept?id=`: labels per language, links, related concepts, the JSON-LD).

### The pick-concepts dialog

Other client modules open it with `IModuleDialogs.ShowAsync("Module.Keywords/pick-concepts", parameters)` (check
`IsAvailable` first: the module may not be installed). Ids are strings.

```
parameters  { multiple?: bool, selected?: ["1"], type?: "Place", language?: "ar", exclude?: ["7"] }
result      { ids: ["1", "4"], concepts: [{ id, name, type, slug }] }   in the order chosen; nothing when cancelled
```

It searches in any language, shows each concept's other names, and lets a `keywords.manage` user add a missing name as
a new concept on the spot. Keep the id and the name you got: the name is a snapshot for display, the id is the link.

## Building

```bash
dotnet build
```

```bash
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform). Add a migration for every
database provider after a model change:

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.Keywords.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.Keywords.Infrastructure.Data.Migrations
```

After an endpoint change, export the module's OpenAPI document again (the entry project is `Web`). The next build of
`WebApi.Modules.Keywords.Client` regenerates the typed client from it (NSwag); commit both, so client changes show
up in review:

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.Keywords.Web -ModuleId keywords `
    -Output <this repo>/src/openapi/keywords.json
```

## Installing

The server part is the build output of `WebApi.Modules.Keywords.Web` (`bin/<Configuration>/net10.0`: every layer
plus the private Mediator and Ardalis.Result). Zip it and upload it on the client's Host Modules page
(`/host-modules`, as a platform admin), then activate it: the tenant migrations run per tenant, the routes are mapped
under `/api/keywords`.

The client parts are two assemblies, uploaded on the client's Client Modules page (`/client-modules`), the API client
first: `soft.square.net.WebApi.Modules.Keywords.Client.dll` (hidden; other client modules may depend on it) and
`soft.square.net.Module.Keywords.dll` (the Keywords pages and the pick-concepts dialog). The playground builds all three for you: `playground/out/keywords.zip`
and `playground/out/client/`.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform               git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.Keywords      this repo
```

(another location: `--property:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080,
client 5070), so stop the lab and any other playground first.

```bash
dotnet run --project playground --launch-profile dev
```

| Profile | What it does |
| --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.Keywords.Web/bin/<Configuration>/net10.0` (`Modules:Local`), and the client parts from their build output (`ClientModules:Local`), Development only: installed and active on start. Change code, rebuild, restart the `webapi` resource in the dashboard |
| `install` | The platform starts without the module, as in production; upload `playground/out/keywords.zip` on http://localhost:5070/host-modules (sign in as the dev platform admin) and activate it, then the two dlls in `playground/out/client/` on http://localhost:5070/client-modules, the API client first |

In Development the platform seeds the tenants `acme` and `globex`. The playground grants the module's permissions in
`acme` to the dev accounts through `Access:DevGrants`: `acme-admin@modular.local` gets `keywords.*`,
`editor@modular.local` gets `keywords.read`. Their passwords are in the platform's
`WebApi.Identity.Server/appsettings.Development.json`. Sign in on http://localhost:5070 as `acme-admin@modular.local`
and open **Keywords**; the API is browsable at http://localhost:5080/scalar.

Data stays in the Docker volume `keywords-playground-data` and in `playground/.data`; delete both to start over.
